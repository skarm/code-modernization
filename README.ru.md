# Code Modernization

[English](README.md) | **Русский**

Неофициальная адаптация [Code Modernization от Anthropic](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)
с исполнением через **официальный `@openai/codex-sdk`**. Сохранены 13 основных команд,
три вспомогательных имени панели, восемь исходных ролей, направления uplift / transform /
reimagine, основные артефакты и человеческие согласования. Лицензия — Apache-2.0, см. [NOTICE](NOTICE).

Текущая версия пакета — `0.1.0`, указанная в `package.json`. Версии SDK и форматов
артефактов учитываются отдельно. Сборка описана в [RELEASING.md](docs/RELEASING.ru.md).

В этой версии SDK — основной исполнитель: отдельные Codex threads выполняют задания,
поток событий фиксирует прогресс, JSON Schema задаёт формат ответов, а `resumeThread`
продолжает незавершённые сессии. Координатором остаётся текущий Codex: он общается с
человеком, готовит входные данные, запускает процедуры и объединяет проверенные результаты.

**Нет Python, SQLite, MCP-сервера, собственного клиента model API или model provider
или фонового сервиса.** В настольном клиенте при интерактивном запуске навыка доступен локальный UI на Node.js.
Терминальный клиент, включая SSH, использует текстовый статус и текущий диалог.
Есть небольшой runner, который реализует порядок исходных
workflow через публичные методы SDK; это не альтернативный агент вместо Codex.
Итоговую проверку свидетельств выполняет отдельный детерминированный Node proof pack:
тесты, P0-трассировка, сравнение поведения, fresh inputs, canary и проверки uplift.

**Проверки:** локальные тесты и команды воспроизведения описаны в
[TESTING.md](docs/TESTING.ru.md). Workflow-тесты используют двойник SDK;
proof pack проверяется на реальных файлах и замороженном эталоне исходного Python-кода.
Совместимость установки описана в руководстве по проверкам; поведение интерфейса —
в [UI.md](references/UI.md). Модульные тесты не подтверждают
весь процесс модернизации с реальной моделью.

Для разработки см. [CONTRIBUTING.md](CONTRIBUTING.ru.md), для сборки дистрибутива —
[RELEASING.md](docs/RELEASING.ru.md). Лицензии и происхождение стороннего кода
сохранены в [NOTICE](NOTICE) и [UPSTREAM.md](docs/UPSTREAM.ru.md).

Сообщайте об уязвимостях приватно через **Security → Advisories → Report a vulnerability**
в репозитории, из которого получен плагин. Если форма недоступна, следуйте
[политике безопасности](.github/SECURITY.ru.md).

## Демонстрация без модели

В папке плагина создайте синтетический workspace и посмотрите текстовый статус:

```bash
demo_workspace=$(mktemp -d)
node examples/ui-demo.mjs "$demo_workspace"
node scripts/modernize.mjs panel --workspace "$demo_workspace" --system carddemo --interface terminal
```

Для локальной браузерной панели выполните последнюю команду с `--interface gui`
и откройте выведенный loopback URL. Завершение — `Ctrl+C`. Через SSH остаётся
терминальный режим. Демо не обращается к модели; результаты и вердикты синтетические.
Изменения карточек и согласований затрагивают только этот временный workspace.

## Требования

Нужны Node.js **20+**, npm для установки закреплённых `@openai/codex-sdk@0.162.1`
XML-парсера `saxes@6.0.0` и `@stephen-riley/pcre2-wasm@1.2.4` для сложных regex masks.
SDK-workflow требуют работоспособного локального Codex
с авторизацией. Локальные `compare` и `verify` работают без входа и обращений к модели.
Сам официальный SDK документирует Node.js 18+; 20+ — минимум именно этого runner.
Сборщик TypeScript и `pip` не нужны; зависимости воспроизводятся через package-lock.json.

Для упаковки релиза также нужен `tar` (Linux/macOS).

SDK по умолчанию запускает закреплённый Codex CLI из своей npm-зависимости: отдельный
глобальный бинарник не требуется. `CODEX_PATH` позволяет явно выбрать другой абсолютный
исполняемый файл; совместимость такого переопределения проверяется отдельно. SDK из общего
каталога должен иметь ту же закреплённую версию. Успешный импорт не проверяет авторизацию.

Codex поддерживает вход через ChatGPT или API key. Этот плагин не требует отдельного ключа,
не копирует `auth.json`, не читает токены вручную и не заменяет механизм входа Codex.
При использовании существующего локального входа обращение идёт через него; **наличие
открытого окна ChatGPT само по себе не доказывает наличие локального CLI и авторизации**.
Проверка `codex login status` не раскрывает ключ в конфигурации плагина. Модельные вызовы
используют лимиты/биллинг выбранного в Codex способа входа, а не становятся бесплатными.

Сборка проекта по-прежнему требует его стека: Go для `go test`, JDK для Java и так далее.
Недоступная сборка остаётся явно невыполненной; SDK не заменяет компиляторы или тестовую БД.

Источники требований, проверенные 15 октября 2026 года:
[SDK README](https://github.com/openai/codex/blob/rust-v0.162.1/sdk/typescript/README.md),
[SDK](https://developers.openai.com/codex/sdk/),
[авторизация](https://developers.openai.com/codex/auth/).

## Установка SDK и плагина

Клонируйте репозиторий или распакуйте релизный архив в постоянную папку
**вне checkout модернизируемого проекта и workspace результатов**.
В ней находятся `.codex-plugin/plugin.json`, `hooks/hooks.json` и локальный
каталог `.agents/plugins/marketplace.json`. Не смешивайте файлы разных версий.

### SDK: обычная установка

В папке плагина:

```bash
npm ci --ignore-scripts --bin-links=false
npm run doctor
```

Это устанавливает закреплённые SDK, XML-парсер и WASM regex backend. `doctor` проверяет
Node, импорт SDK и создание клиента, **но не делает модельный вызов и не проверяет вход**.
`package-lock.json` содержит реальные версии, npm-адреса и integrity установленных пакетов.
`npm ci` воспроизводит закреплённые зависимости; установка не делает модельных вызовов.
`--bin-links=false` обязателен при установке зависимостей внутри каталога плагина:
Codex CLI 0.164.0 пропускает hooks, если при вычислении отпечатка пакета встречает
символьную ссылку `node_modules/.bin/codex`. SDK запускает CLI непосредственно из
закреплённого npm-пакета и не использует эту ссылку.

### SDK: общий каталог для read-only plugin cache

Если приложение копирует плагин в недоступный для записи кэш, поставьте SDK отдельно
в постоянный локальный каталог, поддерживаемый runner:

```bash
mkdir -p "$HOME/.codex/code-modernization-sdk"
npm install --prefix "$HOME/.codex/code-modernization-sdk" \
  --save-exact @openai/codex-sdk@0.162.1
```

Runner ищет SDK сначала рядом с пакетом, затем в
`${CODEX_HOME:-~/.codex}/code-modernization-sdk`. Другой абсолютный каталог можно задать
через `CODEX_MODERNIZATION_SDK_DIR`. Путь относится к npm-проекту, а не к `node_modules`.
Не надо устанавливать SDK заново для каждого запуска/проекта. Пример использует обычный
`~/.codex`; при нестандартном `CODEX_HOME` выберите соответствующий путь.

### Локальный marketplace

Для регистрации и установки уже подготовленного каталога можно использовать Codex CLI:

```bash
codex plugin marketplace add /absolute/path/code-modernization
codex plugin add code-modernization@code-modernization --json
codex plugin list --marketplace code-modernization --json
```

`marketplace add` регистрирует источник; `plugin add` устанавливает сам плагин.
В результате установки поле `installedPath` указывает исполняемую копию. Если её
`node_modules` отсутствует, выполните `npm ci --ignore-scripts --bin-links=false` в этой копии с исходным
`package-lock.json`, затем запустите её `scripts/modernize.mjs doctor`.
Проверка списка должна показать `installed: true` и `enabled: true`.
Команды проверены с установленным Codex CLI 0.162.0-alpha.17.2 15 октября 2026 года.
Если в вашем CLI ещё нет `plugin add`, установите плагин из локального источника через
каталог плагинов приложения. Для загрузки навыков начните новый чат.

При обновлении из другой версионной папки CLI может сообщить, что marketplace уже
добавлен из другого источника. В таком случае выполните
`codex plugin marketplace remove code-modernization`, затем повторите `marketplace add`
с новой папкой и `plugin add` выше. Это переключает только указанный локальный источник.
Старую папку версии можно сохранить для возврата.

Вместо команды `plugin add` можно выбрать **Code Modernization** в `/plugins`
Codex CLI или в Plugins Directory настольного приложения. После изменения локальных
файлов обновите установленную копию и начните новую сессию; приложению может потребоваться
перезапуск. Общий каталог SDK, описанный выше, нужен только когда зависимости нельзя
поставить в исполняемую копию.

Альтернатива — скопировать весь пакет в `~/.codex/plugins/code-modernization/`
и добавить элемент из [marketplace-personal.json](examples/marketplace-personal.json)
в `~/.agents/plugins/marketplace.json`. Сохраняйте чужие записи и имя существующего каталога.
`source.path` считается от корня marketplace (`~` для личного), не от `.agents/plugins`.
Старую установку отключите, чтобы не получить дублирующиеся skills.

Прикрепление ZIP к обычному чату не является установкой. Поддержка локального каталога,
запуска процессов и доступа к проекту зависит от клиента и правил рабочего пространства.
Документированный формат: [упаковка](https://developers.openai.com/plugins/build/plugins),
[использование](https://developers.openai.com/codex/plugins/). Этот дистрибутив не опубликован
в официальном каталоге и не установлен автоматически в ваш аккаунт.

## Первый запуск

В чате Codex с доступом к исходникам и отдельной рабочей папке:

```text
$modernize my-service --source "/Users/me/projects/my-service"

Workspace: /Users/me/modernization/my-service
Цель: uplift.
Используй SDK workflow этого плагина для анализа и проверок.
Сначала выполни preflight, обследуй проект и подготовь план.
Исходники не изменяй. До моего одобрения плана не начинай реализацию.
Отвечай по-русски.
```

SDK уже является режимом по умолчанию. Координатор сам готовит JSON задания, выбирает
нужную процедуру, запускает её через терминал и читает результат. Пользователю не нужно
самостоятельно составлять граф заданий или JSON с согласованиями. При отсутствующем SDK
координатор сообщает причину, а не изображает выполненные вызовы или незаметно переключается
на менее проверяемое исполнение. Установка пакетов требует разрешений текущей среды.

Исходники и workspace должны быть разными невложенными каталогами. Кандидатная версия
находится в `workspace/modernized`, исходная — по ссылке `legacy/<system>` либо по абсолютному
пути в `analysis/<system>/SOURCE`. Human gates остаются явными решениями пользователя в чате, локальном UI и
исходных Markdown-документах, а не придуманными агентом подписями.

## Команды и роли

```text
$modernize                Координатор, выбор/продолжение процесса
$modernize-preflight      Границы, окружение, цель и исходники
$modernize-assess         Обследование системы или портфеля
$modernize-map            Карта компонентов и потоков
$modernize-extract-rules  Бизнес-правила со ссылками на исходники
$modernize-review         Проверка правил и решения человека
$modernize-brief          План, риски и критерии приёмки
$modernize-uplift         Обновление внутри текущего стека
$modernize-transform      Перенос на другую технологию
$modernize-reimagine      Новая архитектура через спецификацию
$modernize-verify         Проверка сохранения поведения
$modernize-harden         Проверка безопасности, без автоматического patch
$modernize-status         Состояние процесса и SDK-запусков
```

Три имени панели сохранены: `$modernize-panel`, `$modernize-review-pane`, `$modernize-sign`.
В CLI и по SSH они работают в терминале: состояние, карточки правил и согласования
показываются в текущем диалоге. Браузер и HTTP-сервер не запускаются.
`node scripts/modernize.mjs panel --workspace DIR --system NAME` печатает текстовое
состояние и завершается; `--json` возвращает JSON. В GUI доступна HTML-панель;
явный запуск сервера использует `--interface gui`. Неопределённый тип хоста выбирает
терминал, SSH/CI остаются терминальными даже при GUI-настройке.
Теперь есть браузерный аналог исходного интерфейса: живая карта модулей, этапы, proof chips,
фазы, следующая команда, карточки ревью с заметками и исходниками, диалог согласования
плана, полный отчёт, topology и fleet SDK-заданий. Согласование плана требует явного
действия человека; проверку VERIFICATION оно не подписывает.

Обновления приходят потоком событий; переподключение восстанавливает актуальное состояние.
Заметки, фокус и раскрытые секции сохраняются. Отчёт и topology обновляются с сохранением
позиции; версию можно зафиксировать для чтения. Fleet показывает очередь, длительность,
ленту команд и изменений, связь с runner и бюджеты. Доступны пауза после активных задач,
продолжение, остановка и повтор упавших задач. Возобновление сохранённого SDK-запуска
требует подтверждения; повторная запись — просмотра частичных изменений и нового согласия.

```bash
node scripts/modernize.mjs panel --workspace /absolute/workspace --system billing
node scripts/modernize.mjs report --workspace /absolute/workspace --system billing
```

При первом использовании Codex должен разрешить новые hooks: установка сама не выдаёт
это доверие. В GUI после этого hooks регистрируют систему, запускают принадлежащую сессии
панель и открывают браузер. Режимы `auto|command|off` и X-ray сохраняются в workspace.
Если hooks недоступны в GUI, навык запускает foreground-панель с `--interface gui`
и открывает напечатанный URL. В CLI используется текстовый статус без браузерного fallback.
В Codex тот же URL можно показать рядом с чатом. Процесс слушает только `127.0.0.1`.
X-ray подключён к поддерживаемым чтениям родителя и SDK; UI видит тесты и ошибки команд.
Кнопки очереди следующего шага и паузы работают через следующий hook, без прав на
произвольные команды. Нативная вставка в prompt и мгновенный interrupt модели не
предоставляются этими hooks. Подробности — [UI.md](references/UI.md).

Пакет использует совместимый `.codex-plugin` layout: загрузчик CLI 0.162.1 игнорирует
hooks при наличии корневого portable `plugin.json`. Portable-пример сохранён в examples;
не копируйте его в корень этой установки.

Все восемь ролей сохранены: `legacy-analyst`, `business-rules-extractor`,
`architecture-critic`, `security-auditor`, `test-engineer`, `version-delta-analyst`,
`uplift-migrator`, `scaffolder`. Их Markdown-инструкции подаются в выделенные SDK threads.
Отдельные контексты не означают разных моделей или статистически независимых экспертов.

## Что теперь исполняется через SDK

**Шесть исходных workflow имеют JavaScript-исполнение, а не только текстовое описание.**
`extract-rules` извлекает правила пакетами или тематическими проходами, проверяет ссылки
и передаёт P0 ещё двум проверяющим. `uplift-deltas` анализирует четыре категории изменений
с проверкой найденных мест. `harden-scan` запускает пять направлений анализа и дополнительные
проверки High/Critical. `portfolio-assess` обследует явно перечисленные системы.

`uplift-migrate` обрабатывает готовые по зависимостям units, ограничивает параллелизм и
останавливает дальнейшие партии при недостаточном числе измеренных успешных сборок.
`reimagine-scaffold` создаёт согласованные сервисные каркасы в непересекающихся каталогах.
Каркас не объявляется готовой работающей системой.

Для остальных действий исходных ролей используется технический адаптер `role-task`:
обследование, проектирование тестов, архитектурная критика, пилот, согласованная реализация
и отдельная оценка результатов. Это не новая бизнес-стадия. Общие файлы проекта, human gates
и итоговые отчёты остаются у координатора, а не у параллельных писателей.

Использованы `startThread`, `resumeThread`, `runStreamed`, JSON Schema `outputSchema`,
отмена через `AbortSignal`, сведения об исполняемых командах/изменениях файлов/usage,
локальные изображения, настройки модели и reasoning effort по ролям, cwd, sandbox,
network и web search. Сеть и web search выключены по умолчанию; для проверки актуальных
версий координатор должен явно выбрать доступный разрешённый способ получения первоисточников.
Версии моделей не подставляются наугад: по умолчанию действует конфигурация Codex.

## Прогресс и продолжение

Основные результаты сохраняются в исходных Markdown/JSON-файлах. Дополнительно:

```text
workspace/
├── legacy/<system>                  # исходники не редактировать
├── analysis/
│   ├── .codex-sdk/coordinator.lock  # один координатор на workspace
│   └── <system>/
│       ├── MODERNIZATION_BRIEF.md
│       ├── BUSINESS_RULES.md
│       ├── VERIFICATION.md
│       └── .codex-sdk/runs/<id>/
│           ├── request.json
│           ├── state.json
│           ├── result.json
│           ├── <task>.result.json  # ответ и свидетельства
│           └── <task>.events.jsonl # поток событий
└── modernized/<candidate>/
```

Базы данных нет. Сохранённые thread IDs позволяют продолжить незавершённые задания через
SDK. Завершённые результаты повторно используются только при совпадении проверяемых входов;
изменение исходников, контекста, настроек ролей или кода исполнителя требует нового запуска.
Это не журнал Claude Workflow и не гарантия exactly-once. Файлы состояния и сессии Codex
содержат чувствительные сведения о проекте: не публикуйте их вместе с репозиторием.

Обычно достаточно `$modernize-status` или `$modernize` с теми же workspace/system.
Для диагностики доступны команды:

```bash
node scripts/modernize.mjs status --workspace /absolute/workspace --system my-service
node scripts/modernize.mjs resume --workspace /absolute/workspace \
  --system my-service --run-id SAVED_RUN_ID
```

После аварийного завершения проверьте, что прежние процессы остановлены, и просмотрите
частичные изменения. Только после этого используется `--confirm-stopped`; для записывающей
процедуры требуется повторный `--allow-writes`. Автоматического повтора незавершённой записи
или самовосстановления по истёкшему lease нет.

## Ограничения и безопасность

Read-only и workspace-write задаются параметрами SDK, а не только текстом роли. Но это
запрос к политике локального Codex/ОС, не самостоятельная песочница плагина. Совместимость
и реальная изоляция хоста здесь не проверены. Записывающие SDK-задания получают отдельные
подкаталоги кандидата; общие manifest/lockfile принадлежат координатору. Не расширяйте права
до полного доступа ради прохождения тестов. Сборочные кэши создавайте в разрешённой области.

Счётчики токенов ограничивают **запуск новых заданий**, а не являются жёстким лимитом счёта:
параллельные незавершённые запросы и ошибки без usage могут дать превышение. Сигналы отмены
передаются SDK; после принудительного завершения ОС проверьте дочерние процессы.

Structured output подтверждает структуру ответа, не истинность. Для сборки и обязательных
тестов миграции runner требует совпадающие события завершённых команд SDK с exit code;
смысл команды, число тестов и покрытие проверяются отдельно. Падение/отсутствие тестов
останавливает дальнейшие партии; исключение требует записи решения человека для unit.
Успешный SDK-run не означает `PROVEN`. Итоговый вердикт вычисляет перенесённый на Node.js
proof pack (`codex-node-proof-pack`), читая реальные отчёты, логи и выходы программ.
Модель не может заменить эти свидетельства своим заключением.

Подробно: [исполнение SDK](references/SDK.md), [безопасность](references/SECURITY.md),
[проверка](references/VERIFICATION.md), [происхождение и адаптация](docs/UPSTREAM.ru.md).

## Механическое сравнение наблюдений

После реального исполнения old/new используйте сохранённый `cases.json`:

```bash
node scripts/modernize.mjs compare \
  --cases /absolute/workspace/analysis/my-service/equivalence/cases.json
```

Команда работает без SDK и модели, пишет `EQUIVALENCE.json` рядом с cases.json и проверяет
байты, обоснованные byte masks, точные десятичные допуски, границы путей и чувствительность
компаратора к мутации. Exit 0 означает успешное сравнение этих наблюдений, 1 — различие или
пробел, 2 — непригодный вход. Одобренные различия сохраняются как `differs-approved`.
Поддерживается совместимое подмножество Python regex masks с Latin-1/байтовой семантикой
и ограничением времени. Неподдерживаемые конструкции дают явную причину `missing`;
границы совместимости перечислены в [VERIFICATION.md](references/VERIFICATION.md).
Команда не запускает проект и не выносит итоговый вердикт сохранения бизнес-поведения.

## Итоговая проверка свидетельств

После реальных тестовых запусков, canary и old/new comparisons:

```bash
node scripts/proof-pack.mjs my-service --workspace /absolute/workspace
# Равнозначная команда основного CLI:
node scripts/modernize.mjs verify --workspace /absolute/workspace --system my-service
```

Создаёт `analysis/my-service/VERIFICATION.json` и `VERIFICATION.md` с вердиктами по
модулям, причинами, свидетельствами, SHA-256 прочитанных файлов и пустым human sign-off.
Exit 0 — `PROVEN`, 1 — `PARTLY PROVEN` / `NOT PROVEN`, 2 — непригодные входные данные.
Движок повторно сравнивает байты, читает JUnit/TRX и логи раннеров, проверяет P0-правила,
не менее 10 новых групп входов и чувствительность canary. Для uplift дополнительно
проверяет измеренный baseline, сохранность тестовых файлов и ссылки на silent deltas.

Аргумент модуля сохраняет исходную семантику: каждый построенный модуль проверяется
заново; имя unit в uplift сужает его suites. Каталоги только с тестовым tooling выводятся
отдельно. Движок не исполняет команды из свидетельств и не исправляет проект.
Полный контракт входов и механические ограничения — в [VERIFICATION.md](references/VERIFICATION.md).

## Проверки пакета

После установки зависимостей локальные проверки выполняются без модельных вызовов:

```bash
npm test
npm run test:proof
npm run check
```

Отдельно предусмотрена **добровольная реальная проверка SDK** после установки и входа:

```bash
npm run smoke:sdk -- --confirm-live
```

Она делает два коротких модельных обращения: создаёт сессию и продолжает её по ID,
проверяя structured output и сохранённый контекст. Использует лимиты выбранного входа.
Без `--confirm-live` обращения не выполняются. Эта проверка не заменяет полноценный
прогон всех workflow на вашем проекте. Охват и ограничения проверок —
в [TESTING.md](docs/TESTING.ru.md).
